# OmniWM

[OmniWM](https://omniwm.app) is the tiling window manager. It also draws the workspace bar, which replaces the macOS menu bar, and the focus border. Its own hotkeys are off: Karabiner drives it through `omniwmctl` and its own helper program ([karabiner.md](karabiner.md)).

## Files

| Path | Tracked | Managed by | Purpose |
|---|---|---|---|
| `.config/omniwm/settings.toml` | yes | hybrid | OmniWM's whole configuration. OmniWM rewrites it from its Settings window; the Karabiner build generates `[[workspaces]]` and the `assignToWorkspace` `[[appRules]]` and keeps every other rule |
| `.config/omniwm/shell/shell.toml` | yes | hybrid | Bar overrides (`[profiles.default]`): widget layout and `workspaceBar` style. OmniWM's Settings window writes it; hand edits apply too |
| `.config/omniwm/shell/widgets/meters/init.luau` | yes | manual | Bar widget showing CPU, GPU, memory, storage and network, see below |
| `.config/omniwm/shell/` (everything else) | no | app | OmniWM-managed profiles, widgets and type definitions, updated with each release |
| `.config/omniwm/helper/*.go`, `go.mod` | yes | manual | The helper's Go sources: one file per action, plus `main.go` (the actions and their arguments), `config.go` (the `OMNIWM_*` settings and their defaults), `ipc.go`, `omniwm.go`, `workspaces.go`, `displays.go`, `pointer.go` and `state.go` |
| `.config/omniwm/helper/omniwm-helper` | no | build | The helper program, built by the Karabiner build (`npm run helper`) and bootstrap step `031` |
| `.config/omniwm/scripts/show-menu-bar.sh` | yes | manual | Turns macOS menu bar auto-hide back off, see below |
| `Library/LaunchAgents/dots.show-menu-bar.plist` | yes | manual | Runs `show-menu-bar.sh` at login and whenever the global preferences change |
| `~/Library/Logs/dots.show-menu-bar.log` | no | scripts | Errors of `show-menu-bar.sh` |
| `.config/karabiner-config/src/apps.json`, `workspaces.ts` | yes | manual | Workspace keys, and each app's workspace and key, see below |
| `~/.local/state/omniwm/`, `~/.local/state/omniwm-helper/` | no | app / helper | OmniWM's runtime state and the helper's pull and send state |

## How it works

### settings.toml

- OmniWM reloads the file on save and rewrites it in canonical form (sorted keys, no comments) whenever a setting changes, so it often shows up as modified. Validation is strict: a missing key, an unknown enum value or a duplicate hotkey id rejects the whole file.
- Values the Karabiner setup relies on: `general.hotkeysEnabled = false` and every binding `"Unassigned"`, `general.ipcEnabled = true` (`omniwmctl` needs it), `niri.moveWindowStacksIntoColumn = false` (the move keys swap columns, the join keys consume or expel), `workspaceBar.hideEmptyWorkspaces = true` (39 workspaces exist), `quakeTerminal.enabled = true` with `provider = "ghostty"` (Hyper + ⏎), the app rules not generated by the build (minimum window sizes, floating 1Password, which Hyper + p toggles, and Burp's Settings window), and ⌃⌘-drag to move or resize tiled windows. Everything else (gaps, border, animations, gestures, default layout) is plain preference.
- The bar uses OmniWM's default shell style, which `shell/shell.toml` moves to the bottom edge (`position = "bottom"`, full width). The style's own `[workspaceBar]` in `shell/default/shell.toml` overrides the matching `settings.toml` keys, so bar position, height, width, background and labels belong in `shell/shell.toml`.
- `shell/shell.toml` also picks the widgets: `workspaces` and `scratchpads` on the left, `active-window` in the center and `meters` on the right. The style's `stats` widget shows only CPU and memory, so `meters` is our own: it reads CPU, GPU, memory, disk and the network rates from `ctx.data`, turns a reading of 90 % or more orange, and opens the style's stats panel on click. Widgets in `shell/widgets/` see `shell/` laid over the profile folder, so they load the style's libraries with the same paths as its own widgets (`require("../lib/look")`). `omniwmctl query shell-widgets` shows whether a widget loaded and its error otherwise.
- The macOS menu bar always shows. OmniWM 0.8.0 turns on macOS menu bar auto-hide for every full-width bar not set to `belowMenuBar`, even at the bottom ([OmniWM#1270](https://github.com/OmniNull/OmniWM/issues/1270)), and restores it on quit; its `apple-menu` and `app-menu` widgets render only while it does. The `dots.show-menu-bar` LaunchAgent watches `~/Library/Preferences/.GlobalPreferences.plist` and runs `show-menu-bar.sh`, which turns auto-hide off again within a second or two. OmniWM sets auto-hide only when its own request changes (at launch, on a settings reload that turns it on, after a Hidden Bar menu closes), so the two don't fight. Auto-hide set in System Settings is undone too. A bar that isn't full width needs neither.
- `routing.mode = "macOS"` makes OmniWM follow the macOS display arrangement, which the helper relies on (below). `routing.arrangements` holds Monitor Setup's grids, keyed by this machine's display UUIDs, and only matters in `custom` mode.

### Workspaces and apps

- Workspace keys are `1–9`, `0`, `a–z`, `ä ö ü`, in that order (`workspaceKeys` in `workspaces.ts`). OmniWM only accepts positive integers as names, so the key at position *i* becomes workspace `i + 1` with the upper-case key as `displayName` (`1` → `1`, `0` → `10`, `a` → `11`/`A`, `ü` → `39`). Native `omniwmctl` calls use the number, resolved at build time; the helper takes keys and looks workspaces up by display name.
- OmniWM numbers its scratchpads 1–10. Right ⌘ + digit toggles one and right ⌘⌥ + digit toggles the focused window's assignment to it, with `0` as scratchpad 10 like workspace 10.
- New workspaces get the home monitor `main`, except `8` (`secondary`) and `9` (`tertiary`), and the layout `default`. A home changed later in OmniWM's Settings window survives the build.
- `apps.json` lists the apps, each as `{ "workspace": "t", "key": "t", "bundleId": "…" }`. `workspace` is the app's default workspace, which several apps can share. `key` is optional and independent of `workspace`: it doesn't have to match it, and several apps can share a key, on the same workspace or on different ones. An app without a key (Rex) gets its workspace but no Hyper binding. The workspace feeds the generated `assignToWorkspace` rules (OmniWM applies them only while the app has no windows, so its first window lands there) and the helper's `send-window default` / `move-all-to-default` (unlisted apps go to `q`). Any workspace key, digit or letter, can be an app's key; the digits have none by default. The key feeds Karabiner: Hyper + key returns to the last focused window of the key's apps (OmniWM's `focus-rank`), or launches the first of them in `apps.json` order when none has a window. While one of their windows has focus, it steps back through the focused app's windows (by workspace, then window id, the same direction as pull), then on to the next app in `apps.json` order, wrapping around after the last; an app without windows is one stop that launches it. With apps A and B, presses go through A's windows, B's windows, back to A, and a closed app is opened when its turn comes. Hyper + a key without an app switches to that key's workspace (`p` toggles 1Password instead). ⌘ + Hyper + key pulls one of the key's apps' windows to the workspace under the pointer; pressing it again within `OMNIWM_PULL_RESTORE_SECONDS` (5 s) sends that window back and pulls the next one, while pulling another key's apps leaves it where it is. ⌥ + Hyper + any workspace key pulls that workspace to the display under the pointer, and ⌥⌘ + Hyper + any workspace key sends the focused window there without following it; pressing it again within `OMNIWM_FOLLOW_SECONDS` (0.5 s) follows the window. ⌘ + Hyper + ␣ does the same for the window's app's workspace.

### Helper

- Bindings use a native `omniwmctl` command whenever one does the job. Actions that need state or several requests run `omniwm-helper <action>`, a Go program with one file per action (`cycle.go`, `pull.go`, `summon.go`, `send_window.go`, …). It talks to OmniWM's IPC socket itself instead of starting `omniwmctl` for every request (about 5 ms each), so most actions take 3–4 ms. It reads its settings from `OMNIWM_*` environment variables (defaults in `config.go`), prints errors on stderr and exits 1. `cycle` and `toggle` launch an app themselves (`open -b`); Karabiner opens a key's first app only when `cycle` fails, e.g. while OmniWM isn't running.
- OmniWM doesn't document its IPC protocol: one JSON line per request to `~/Library/Application Support/com.barut.OmniWM/ipc.sock`, authenticated with the token in `ipc.sock.secret` next to it, at protocol version 22 (`ipc.go`, `omniwm.go`). `omniwmctl` speaks the same protocol, so after an OmniWM update that changes it, point `OMNIWM_SOCKET` at a socket that logs requests to see what `omniwmctl` sends now.
- Moving the focused window with the `move-to-workspace` command doesn't make focus follow it, which `send-window` relies on to send a window to a background workspace. A second press follows with `window navigate`. Presses take turns through an `flock` on `send.lock` in the state folder, because a quick second press starts while the first still runs; the kernel releases it even when the helper crashes. Every IPC request times out after 2 s, so a hung OmniWM fails the action instead of blocking every press behind it.
- OmniWM moves a workspace only to an *adjacent* monitor (`workspace move-to-monitor` with `force`, a runtime override that a settings reload clears). The helper finds a route over adjacent monitors from the display frames, picking each direction's neighbor the way the macOS routing mode does, hops along it and restores what the displays in between showed (`displays.go`). A `custom` routing grid would make it pick different neighbors than OmniWM.
- The helper reads the pointer through CoreGraphics (`pointer.go`). It loads CoreGraphics only for the actions that need the pointer (`pull`, `summon`), because loading it at every start would add several milliseconds to every action.
- The pointer stays where it is when focus changes: OmniWM's `focus.moveMouseToFocusedWindow` is off, and no helper action moves it.

## Changing it

- Change preferences in OmniWM's Settings window. When a value must be set by hand, change it in place and never delete keys.
- Workspaces and app rules: edit `apps.json` or `workspaces.ts`, run the Karabiner build, and stage `apps.json`, `karabiner.json` and `settings.toml` together. Find a bundle ID with `mdls -name kMDItemCFBundleIdentifier -r /Applications/<App>.app`.
- Only append to `workspaceKeys`. Inserting a key renumbers every later workspace, and OmniWM keeps windows on their workspace *number* across a reload.
- Every write of `settings.toml` makes OmniWM reload, which drops runtime workspace-to-monitor moves; the build skips unchanged writes for this reason.
- Helper: edit its Go files and run the Karabiner build, or `npm run helper` in `~/.config/karabiner-config` to rebuild only the helper. Bindings use the new program at once.
- Track only files you add under `shell/`. The `a` simlayer opens the folder (`c`) and restarts OmniWM (`r`).
- After editing the LaunchAgent, reload it: `launchctl bootout gui/$(id -u)/dots.show-menu-bar; launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/dots.show-menu-bar.plist`. Once #1270 is fixed, boot it out and delete it with `show-menu-bar.sh`.

## Per-machine setup

- Grant OmniWM Accessibility and Input Monitoring.
- Turn on Start at Login in OmniWM's Settings (macOS stores it, not `settings.toml`).
- Keep "Displays have separate Spaces" on, and run Monitor Setup when the displays change.
- The helper program isn't tracked: bootstrap step `031` builds it, or run `npm run helper` in `~/.config/karabiner-config`.
